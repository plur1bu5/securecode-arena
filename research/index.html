Are Small Language Models Safe Coders? A Defensive Benchmark of AI-Generated Code Security

Abstract

Small Language Models (SLMs) are increasingly used to generate code in resource-constrained settings, but whether that code is secure remains largely unmeasured. Prior work (Hasan et al., 2026) evaluated 20 SLMs on functional correctness, efficiency, and language coverage, and explicitly did not evaluate security. We close that gap. We asked 9 models (3 local SLMs and 6 cloud LLMs) to implement 16 neutral functional coding tasks (6 projects across Python, Go, and JavaScript) that carry natural security-sensitive contexts, with no security wording in any prompt. Every generated file passed a parse/compile gate, then was scanned with Bandit, Gosec, and Semgrep, deduplicated on (CWE, line), and classified by severity. We find that the three SLMs produce code with a targeted HIGH/MEDIUM vulnerability on 31.2% of prompts on average, versus 15.6% for the six LLMs, a roughly 2× gap on this sample. Command injection, insecure deserialization, and cleartext transmission are the most frequent classes. The results suggest that compact models are not only cheaper to run but also more likely to emit vulnerable code on this benchmark, and that static analysis of generated code is a necessary, not optional, step.

1. Introduction: the problem

AI-generated code now ships in production, but most benchmarks score models on whether the code works, not whether it is safe. A function can pass every unit test and still concatenate SQL, spawn a shell with untrusted input, or deserialize network data with pickle. Hasan et al. (2026) made this gap explicit: their metrics for SLMs cover pass@k, VRAM, and latency, and "do not account for the security of generated code."

Related agent-scale work, including LSCBench (Wu et al., 2026), likewise finds that functional pass rates far exceed the rate at which generated code is both functional and secure. That evaluation covers frontier agents at function, file, and repository granularity. The present study is complementary: it measures local SLMs against cloud LLMs on a shared, security-neutral prompt set, under a static-analysis protocol designed for generated snippets rather than full agent trajectories.

SLMs matter here precisely because they run on modest hardware (a laptop, a phone, a CI runner) where a human reviewer is least likely to be present. If a 1.5B model is both the cheapest option and the most likely to emit an injection bug, that is a decision a practitioner needs to make with data, not intuition.

This benchmark measures one thing: when a model is asked only for functionality, how often does it introduce a security vulnerability on its own, with no prompting in either direction?

2. Research questions

RQQuestionHow we measure
RQ1How often do SLMs vs LLMs generate vulnerable code?Share of prompts with ≥1 targeted HIGH/MEDIUM finding, per model
RQ2Which vulnerability classes (CWEs) dominate?Distribution of deduplicated findings per CWE
RQ3Does programming language change the vulnerability rate?Per-language targeted HIGH/MEDIUM rate, SLM vs LLM
RQ4Do SLMs produce more vulnerable code than LLMs? (descriptive)Mean vulnerable-prompt rate per group
RQ5Does code size (LOC) predict finding count?Findings per 100 LOC, per language

Framing constraints, stated up front:

  • RQ4 is descriptive only. Nine models is far too small for significance testing, and the SLM-vs-LLM comparison is confounded by provider alignment and unknown browser sampling temperature. We report means and effects, not p-values.
  • Repetitions (3 per prompt) measure within-model reliability, not independent samples.

3. Method

3.1 Models

Nine models. Three local SLMs run via Ollama on CPU: Qwen2.5-Coder 1.5B, Qwen2.5-Coder 7B, and Llama 3.1 8B (a general-purpose control). Six cloud LLMs via browser chat: Claude Sonnet 4.5, DeepSeek V4 Pro, GPT-5.6 Luna, Gemini 3.5 Flash-Lite, Qwen3-Coder Next, and Grok 4.7. The Qwen family forms a deliberate size ladder: 1.5B → 7B → Qwen3-Coder Next.

3.2 Prompts: neutral, functional, identical

Six projects, each a realistic task a developer would ask an assistant for. Five run in Python, Go, and JavaScript; the sixth (a Fibonacci control) is Python-only, giving 16 prompts. Every prompt requests functionality only. It never mentions security, sanitization, hashing strength, or injection. Asking a model to "write vulnerable code" tests instruction-following, not what it emits when a real developer asks for a feature. Prompts are identical across models; only the language and framework change. Zero-shot, temperature 0.2 for SLMs, three repetitions per prompt in a fresh chat or fresh process each time.

The six tasks were not chosen arbitrarily. We began with the MITRE CWE Top 25 and selected the subset that (a) arises naturally in code a developer would actually request, (b) is detectable by static analysis without execution, and (c) spans the three target languages. This gave us the five security-sensitive projects: an authentication API (CWE-522, hard-coded credentials), a file service (CWE-22 path traversal, CWE-73), a database search endpoint (CWE-89 SQL injection), a health-monitor webhook (CWE-78 command injection, CWE-502 deserialization), and a session handler (CWE-319 cleartext, CWE-79 XSS). The Fibonacci control (CWE-free by design) gives a baseline: a model that produces zero findings on a trivial prompt is at least not systematically broken. Prompts were reviewed internally before data collection to confirm that no security-related wording had crept in; the final versions are what appear in the appendix of the full dataset.

3.3 The pipeline

  1. Functional gate. Every file must parse or compile (ast.parse, gofmt -e, node --check). Failures are excluded: a truncated file is neither secure nor vulnerable; it is invalid.
  2. Static analysis. Bandit (Python), Gosec (Go), Semgrep (all three), pinned versions.
  3. Cross-tool deduplication. The same CWE on the same line is often flagged by two tools; we keep the highest severity and record all contributing tools, so Python and Go are not biased upward versus single-tool JavaScript.
  4. Three measurement levels. All findings, then targeted (only CWEs the project was designed to provoke), then targeted HIGH/MEDIUM (the ranking metric). Generic noise (debug=True, subprocess import, no-timeout requests) is filtered out of "targeted".

4. Results

The headline metric is secure rate: the share of a model's 16 prompts that produced no targeted HIGH or MEDIUM finding in any of three repetitions. Higher is better.

Four cloud LLMs (Claude Sonnet 4.5, GPT-5.6 Luna, Grok 4.7, and Qwen3-Coder Next) tie at the top with 14 of 16 prompts secure (87.5%). All three SLMs land at 11 of 16 (68.8%), a full three prompts behind. DeepSeek V4 Pro (12/16) and Gemini 3.5 Flash-Lite (13/16) sit in between.

Grouping by type, the gap is clean: SLMs average a 31.2% vulnerable-prompt rate against 15.6% for LLMs, exactly 2×. We report this descriptively; it is a trend over 9 models, not a population claim, and the LLM edge is plausibly as much about alignment and safety training as raw capability.

4.1 Which vulnerabilities appear most (RQ2)

The most frequent classes are CWE-319 (cleartext transmission: serving HTTP without TLS, 96 findings), CWE-94 (debug code / code injection: Flask debug=True, 82), CWE-502 (insecure deserialization: pickle/eval, 72), and CWE-78 (command injection, 51). CWE-319 and the debug-code class are near-universal across both SLMs and LLMs. They are the defaults a model reaches for when writing an API quickly. The classes that actually discriminate (SQL injection, CWE-89; command injection, CWE-78; insecure deserialization) are where the SLMs lose ground.

4.2 Language (RQ3)

Python is the worst language for both groups (SLMs 44.4%, LLMs 19.4% of prompts vulnerable), expected, since the deserialization and command-injection prompts are Python-native. Go is the safest (SLMs 13.3%, LLMs 0.0%). JavaScript sits between (SLMs 33.3%, LLMs 26.7%), though its rates should be read with caution: JavaScript is covered by Semgrep only, versus two tools for Python and Go, so some findings may go undetected. This mirrors Hasan et al.'s finding that SLMs are weakest on Go: weak proficiency does not translate to more vulnerabilities here; the language's own constraints (typed, no eval, no shell-by-default) are doing protective work.

4.3 Severity (RQ2)

Every model emits a long tail of LOW findings; the discrimination is in HIGH and MEDIUM. SLMs produce HIGH findings at a rate comparable to or above several LLMs. Qwen2.5-Coder 1.5B records 13 HIGH, versus 0 for GPT-5.6 Luna and Grok 4.7, which almost never produce a HIGH-severity finding at all.

5. Discussion

Three takeaways.

1. Size tracks security, but not the way one might assume. The gap is not that large models are safer because they are more capable. It is that the most aligned models (GPT-5.6 Luna and Grok 4.7 record zero HIGH findings; Claude and Qwen3-Coder are close behind) tend to avoid the dangerous construct, while the small local models default to it. The alignment advantage is not uniform across all four top LLMs, but the pattern is consistent enough to be worth noting. The smallest model in the set, Qwen2.5-Coder 1.5B, is no worse than Llama 3.1 8B. Size within the SLM group does not buy security.

2. The dangerous constructs are habits, not bugs. CWE-319 (no TLS) and CWE-94 (debug=True) dominate because they are the default shape of a quickly written API. A model does not decide to be insecure here; it reaches for the shortest path. This is exactly what static analysis catches well, and exactly what a reviewer skimming for "does it work" misses.

3. The valid/invalid distinction is itself a finding. Before we re-ran the local models, a large fraction of their output did not even parse. Earlier runs showed 41.7% valid for the 1.5B model. After correction, validity is near-universal. The earlier state is the honest picture of a small local model under real use: sometimes it does not produce runnable code at all. That failure mode is separate from, and arguably more important than, writing vulnerable code.

6. Limitations

  • Static analysis only. We do not execute generated code, so behavioral vulnerabilities that static tools cannot see (missing authentication, CWE-287; missing authorization, CWE-862; session fixation, CWE-384) are not measured here. The secure rate is a lower bound on how insecure the code actually is.
  • Small N. Nine models. No causal or statistical claims. The SLM-vs-LLM gap is descriptive and confounded by alignment training and unknown browser sampling temperature.
  • Manual prompt delivery. Browser models were prompted by copy-paste, not an API, so exact sampling settings are uncontrolled (recorded as "unknown").
  • Static analyzers have false positives and negatives. The three-level filter mitigates false positives; Semgrep, Bandit and Gosec overlap mitigates false negatives. Neither is a proof of ground truth.
  • Three repetitions at low temperature. More repetitions could move a borderline prompt across the line. We report repetition-level agreement for this reason.
  • Language selection. Python, Go and JavaScript cover a useful spectrum but not the full language space.
